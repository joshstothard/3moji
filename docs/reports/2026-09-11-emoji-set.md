# Emoji Set candidate: which emoji render on both iOS and Android

**Type:** Research
**Date:** 2026-09-11
**Author:** Josh Stothard (with Claude)
**Status:** Draft
**Related:** #9 (this research), #8 (3moji MVP map); blocks #13, #14, #18

## Question

Which emoji can safely form a Handle: what is the candidate **Emoji Set**, and which Emoji version should it be pinned to so that every Handle renders on both iOS and Android for the OS versions still in common use?

## Summary

- **Pin the Emoji Set to Emoji 12.0** (Unicode, March 2019). Every emoji in it renders natively on iOS 13.2+ (October 2019) and Android 10+ (September 2019). Those floors cover effectively all iOS devices and 91.1% of Android devices in circulation (April 2026 data) [8][9][12][13].
- Applying the ticket's constraints to Unicode's own data gives **1,053 emoji**: single codepoint, `fully-qualified` in `emoji-test.txt`, `Emoji_Presentation=Yes` in `emoji-data.txt`, introduced at or before E12.0, minus the four single-codepoint flags and the one single-codepoint keycap (`U+1F51F keycap: 10`) [1][2].
- Namespace at that size: 1,053 one-emoji Handles, 1,108,809 two-emoji Handles, **1,167,575,877 three-emoji Handles** (ordered, repetition allowed); 1,168,685,739 Handles of length one to three. Without repetition the three-emoji count is 1,164,251,556.
- Every candidate has exactly one CLDR short name, and those names are unique across the set, so each Spoken Name is the CLDR name unchanged [1][3]. Many names differ from a neighbour only by a qualifier (the thirteen `face-smiling` emoji, for example), which is a separate Spoken-Name distinctness problem for #13/#14.
- Some single-codepoint emoji look materially different on Apple and Google. The evidence base for a fixed exclusion list is thin (one peer-reviewed 2016 study on 22 faces [16], plus documented design reversals such as `U+1F52B` [17][18]). Recommendation: keep them in the candidate set, carry the flag list below into the next research step, and decide exclusions there with a side-by-side render of both platforms' current glyphs.
- Moving the pin to Emoji 13.0 (Android 11+ / iOS 14.2+) adds 55 emoji (5%) and drops Android reach from 91.1% to 86.9%; Emoji 11.0 (Android 9+ / iOS 12.1+) drops 61 emoji for +2.4 points of reach. Neither trade is worth it today.

## Background

A Handle is an ordered sequence of one to three emoji drawn from the Emoji Set. A Handle is shown on screen and said aloud, so an emoji that renders as tofu on one platform, or as a different picture, breaks the product's core promise. The ticket fixed the constraints: single-codepoint emoji only (no skin-tone modifiers, ZWJ sequences, keycaps, or flags), must render on both iOS and Android for OS versions still in common use, and exactly one canonical Spoken Name per emoji. There is no `docs/architecture/` yet; this report is the first evidence for the Emoji Set.

Emoji versions are numbered by Unicode: E0.6 through E5.0 were the pre-2018 releases; from 2018 Unicode aligned emoji version numbers with the Unicode version (E11.0 = Unicode 11.0, and so on). Each vendor ships support for a version in a specific OS release, usually months after Unicode publishes it.

## Findings

### Finding 1: Unicode's data defines the candidate mechanically

`emoji-test.txt` (E17.0, dated 2025-08-04) lists every RGI emoji with a status and the emoji version it was introduced in; `emoji-data.txt` (dated 2025-07-25) gives the `Emoji_Presentation` property [1][2]. A Python script (`build.py`, reproduced in Sources) applied the constraints:

| Step                                                                          | Count |
| ----------------------------------------------------------------------------- | ----: |
| Rows in `emoji-test.txt`                                                      | 5,225 |
| Single-codepoint rows                                                         | 1,400 |
| of which `fully-qualified` (rest: 207 `unqualified`, 9 `component`)           | 1,184 |
| of which `Emoji_Presentation=Yes`                                             | 1,184 |
| `Emoji_Presentation=Yes` codepoints in `emoji-data.txt`                       | 1,219 |
| difference: 26 regional indicators, 5 skin-tone modifiers, 4 hair components  |    35 |

So "single-codepoint, fully-qualified" and "single-codepoint, `Emoji_Presentation=Yes`" pick out the same 1,184 emoji: the 207 unqualified single-codepoint rows are exactly the characters that need `U+FE0F` to display as emoji, and the ticket already excludes those. Two further removals follow from the ticket's wording: the four single-codepoint flags in the `Flags` group (`U+1F3C1` chequered flag, `U+1F6A9` triangular flag, `U+1F38C` crossed flags, `U+1F3F4` black flag) and the one single-codepoint keycap, `U+1F51F` keycap: 10 (the other keycaps are three-codepoint sequences and never entered the list). 125 of the candidates are `Emoji_Modifier_Base` (they accept a skin tone); on their own they render in the vendor's default yellow, so they stay in.

### Finding 2: Set size and namespace by pin

Cumulative single-codepoint, fully-qualified count at each Emoji version, from the same script (before the flag/keycap removals):

| Pin   | Set size | Added in version | 3-emoji Handles |
| ----- | -------: | ---------------: | --------------: |
| E5.0  |      935 |               56 |     817,400,375 |
| E11.0 |      997 |               62 |     991,026,973 |
| E12.0 |    1,058 |               61 |   1,184,287,112 |
| E13.0 |    1,113 |               55 |   1,378,749,897 |
| E14.0 |    1,150 |               37 |   1,520,875,000 |
| E15.0 |    1,170 |               20 |   1,601,613,000 |
| E16.0 |    1,177 |                7 |   1,630,532,233 |
| E17.0 |    1,184 |                7 |   1,659,797,504 |

(E12.1, E13.1 and E15.1 added only sequences, so they add no single-codepoint emoji.) After removing the flags and keycap, the E12.0 set is **1,053**, giving 1,108,809 two-emoji and 1,167,575,877 three-emoji Handles. Every pin from E5.0 upward gives a nine-digit three-emoji namespace; the pin choice moves the count by less than a factor of two, so reach should decide it, not namespace size.

Group breakdown of the recommended set: Objects 183, Travel & Places 161, Smileys & Emotion 139, Symbols 138, Animals & Nature 126, People & Body 125, Food & Drink 113, Activities 68.

The important structural fact is from Google's own developer documentation: "Android versions 11 (API level 30) and lower can't update the emoji font" [25]. From Android 12 the emoji font is updatable through Google Play system updates, so an Android 12 device today shows E17.0 emoji even though Android 12 shipped with E13.1 (on devices with Google Play; AOSP-only devices are unverified). Below Android 12 the shipped version is the ceiling unless the app bundles `androidx.emoji2`, which only helps inside that app [25]. A Handle pasted into a third-party messaging app on Android 10 renders with the system font, so for this product the shipped version is the floor that matters.

### Finding 4: Which OS versions are still in common use

StatCounter, August 2026, worldwide mobile [8][9]:

- iOS: 26.6 34.35%, 26.5 33.09%, 18.7 10.38%, 26.3 2.34%, 26.2 2.07%, 18.6 1.82%; everything older is below 2% each. StatCounter notes Safari anti-fingerprinting misreports some iOS 26.x as 18.x, so the 18.x figures are upper bounds. Every listed version is at or above iOS 18.4 (E16.0); the E12.0 floor of iOS 13.2 excludes nothing measurable.
- Android: 16 25.76%, 15 16.91%, 13 14.75%, 14 13.09%, 12 10.07%, 11 8.31%.

Cumulative Android reach by minimum version (apilevels.com, computed from StatCounter April 2026 data) [26]: Android 12+ 78.8%, **Android 11+ 86.9%**, **Android 10+ 91.1%**, Android 9+ 93.5%.

Mapping through Finding 3:

| Pin   | Android floor | Android reach (Apr 2026) | iOS floor | Cost vs E12.0 |
| ----- | ------------- | -----------------------: | --------- | ------------- |
| E11.0 | Android 9     |                    93.5% | iOS 12.1  | -61 emoji     |
| E12.0 | Android 10    |                    91.1% | iOS 13.2  | 0             |
| E13.0 | Android 11    |                    86.9% | iOS 14.2  | +55 emoji     |
| E14.0 | Android 12 (with Play font update) | 78.8% | iOS 15.4 | +92 emoji  |

Android 10 (2019) is the oldest version still above a few percent of the installed base; Android 9 is 2.4 points behind it. The ticket's phrase "oldest OS versions still in common use" therefore lands on Android 10 / iOS 13.2, which is exactly the E12.0 floor.

### Finding 5: Single-codepoint emoji that render materially differently across platforms

UTS #51 acknowledges that "the shape of the character can vary significantly" between vendors and asks designers to keep the same core shape because divergence changes meaning across platforms [27]. The only peer-reviewed measurement found is Miller et al. (ICWSM 2016), which surveyed 304 US participants on 22 popular anthropomorphic emoji across Apple, Google, Microsoft, Samsung and LG renderings [16]. Its across-platform findings, by codepoint:

- `U+1F601` beaming face with smiling eyes: Apple vs each other platform had "platform-pair sentiment misconstrual scores larger than 4.7" (on a 0-10 scale) while the others agreed (below 2); the Google rendering was described as "blissfully happy", the Apple one as "ready to fight".
- `U+1F634` sleeping face: 91% agreed the Microsoft rendering was negative but there was a 68% chance Samsung's would be rated positive or neutral.
- `U+1F64C` raising hands: "in the top three most different renderings for four of our five platforms"; described as "hand, celebrate" (Apple), "praise, hand" (LG), "exciting, high" (Microsoft).
- The 22 studied, in decreasing order of across-platform sentiment disagreement (Figure 1): `1F606 1F64C 1F605 1F60C 1F60F 1F64F 1F631 1F648 1F60E 1F601 1F609 1F612 1F602 1F629 263A 1F60B 1F622 1F618 1F60A 1F62D 1F60D` (`U+263A` is not in our set: it needs `U+FE0F`).

Two caveats. The study measured 2016 glyphs; Google redesigned its entire face set in 2017-2018 and both vendors have revised faces since, so the specific disagreements may no longer hold. And it covers only faces and hands, not objects.

Documented design reversals on a single codepoint:

- `U+1F52B` (CLDR name now "water pistol"): Apple replaced its revolver with a water pistol in 2016; Google and Samsung followed in 2018 [17][18]. Apple and Google now agree (Android 10 shipped after Google's 2018 change, so every version inside our floor shows the toy), but X/Twitter reverted to a firearm in 2024 [18], and OEM fonts such as Samsung One UI are unverified.

Recommended **flag list** (keep in the candidate JSON, decide in the next step with a side-by-side render of current Apple and Google glyphs): `U+1F601`, `U+1F634`, `U+1F64C`, `U+1F606`, `U+1F605`, `U+1F60C`, `U+1F60F`, `U+1F64F`, `U+1F631`, `U+1F648`, `U+1F52B`. Also flag these categories whose Spoken Names describe text rather than a picture and whose glyphs are typographic on both platforms: the 29 `Symbols/alphanum` emoji (for example `U+1F250` Japanese "bargain" button, `U+1F18E` AB button (blood type)), and the 30 `Symbols/geometric` coloured shapes, which are hard to distinguish aloud ("red circle" / "red square" / "red triangle pointed up"). Excluding both subgroups would take the set to 994. Samsung, Huawei and other OEM emoji fonts are out of scope for this report (unverified).

## Options

| Option                           | Pros                                                                                | Cons                                                              | Effort | Risk |
| -------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------ | ---- |
| A: Pin E12.0 (1,053 emoji)       | Renders on Android 10+ (91.1%) and iOS 13.2+; 1.17 billion three-emoji Handles      | Misses 131 newer emoji (melting face, pink heart, etc.)           | Low    | Low  |
| B: Pin E13.0 (1,108 emoji)       | +55 emoji, includes 2020 additions                                                  | Drops Android 10 (4.2 points of reach); Android 11 cannot update its font | Low | Medium |
| C: Pin E11.0 (992 emoji)         | +2.4 points of Android reach (Android 9)                                            | -61 emoji for a version that is two points of share               | Low    | Low  |
| D: Pin E14.0+ and rely on Play font updates | Largest set                                                              | Android 11 and lower (13.1% of Android devices) show tofu for newer emoji | Low | High |

## Recommendation

Pin the Emoji Set to **Emoji 12.0** and adopt the 1,053-emoji candidate list in `2026-09-11-emoji-set.candidates.json` as the Emoji Set's starting point. Confidence is high on the mechanics (the set is derived from Unicode's files by a reproducible script) and on the OS floors (each version-to-release mapping has a primary or near-primary source). Confidence is moderate on the reach figures, which come from StatCounter's browser-based sampling via apilevels.com rather than from Apple or Google. The cross-platform rendering flag list is deliberately a flag list, not an exclusion list: the only measured evidence is a decade old.

What would change the recommendation: Android 10 falling below roughly 3% of devices (then E13.0 becomes the better trade), or the product deciding that Handles are only ever rendered inside the app's own web view with a bundled emoji font (then the OS floor stops mattering and E15.0 or later is fine). Re-check the reach numbers before each yearly review of the pin.
