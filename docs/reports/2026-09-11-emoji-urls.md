# How emoji survive in URL paths on Vercel and Next.js

**Type:** Research
**Date:** 2026-09-11
**Author:** Josh Stothard (with Claude)
**Status:** Final
**Related:** #12 (this ticket), #8 (3moji MVP map), #14 (blocked by this report)

## Question

How does a Handle like `3moji.me/🧊🧊🧊` survive the trip through browsers, Vercel, and the Next.js 16 App Router, and what canonicalisation makes every spelling of the same Handle resolve to one Profile?

## Summary

- **Browsers never send raw emoji.** The WHATWG URL parser UTF-8 percent-encodes every code point above U+007E in a path, so the request line for `3moji.me/🧊🧊🧊` is always `/%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A`. Browsers percent-decode again for display, so the user sees the emoji in the address bar and (mostly) when pasting [S1, S2].
- **Next.js 16.3.4 hands `params.handle` to the page still percent-encoded** (`"%F0%9F%A7%8A…"`, length 36, not `"🧊🧊🧊"`), identically in `next dev` and after `next build` / `next start`, whether the client sent percent-encoded or raw UTF-8 bytes. `request.nextUrl.pathname` in `proxy.ts` is also percent-encoded. A malformed sequence (`/%F0%9F`) is a 400 in dev and a 500 in production. The page must `decodeURIComponent` itself [S3, S4, S5].
- **`redirect()` / `permanentRedirect()` with a raw-emoji path crash with a 500** (`TypeError: Invalid character in header content ["location"]`, `ERR_INVALID_CHAR`) in both dev and production; with the percent-encoded path they work (`307` / `308`, `location: /%F0%9F%A7%8A…`). `<Link href="/🧊🧊🧊">` renders the raw emoji into the `<a href>` and leaves encoding to the browser. `generateMetadata` resolves `alternates.canonical` and `openGraph.url` through `new URL()`, so the emitted tags are percent-encoded [S3, S6, S7, S8].
- **Unicode:** NFC/NFD are no-ops for single-codepoint emoji and do not remove U+FE0F, so normalisation alone cannot merge `🧊` and `🧊️`. VS16 only has meaning on the 371 characters in `emoji-variation-sequences.txt`; keyboards may emit it for text-default emoji such as `❤` (U+2764). A canonical key therefore has to strip U+FE0E/U+FE0F explicitly and validate every code point against the Emoji Set; a Postgres `UNIQUE` on that key is byte equality under a deterministic collation, so it is only meaningful if the application canonicalises before every write [S9, S10, S11, S12].
- **Recommendation:** decode → NFC → strip VS15/VS16 → split into code points → require 1–3 code points, each in the Emoji Set → the canonical key is that code-point sequence. If the received path is not byte-identical to `encodeURIComponent(canonical)`, `permanentRedirect` (308) to the canonical percent-encoded path; if it cannot be canonicalised, `notFound()` (404). Sharing: Apple's link detector keeps the whole emoji URL, `twitter-text` truncates it to `https://3moji.me/`, and WhatsApp and Slack behaviour is unverified, so every share affordance should offer the percent-encoded form as well.

## Background

The map (#8) settled that `3moji.me/🧊🧊🧊` is the canonical URL of a Handle, that a Handle is an ordered sequence of one to three emoji from a curated Emoji Set of single-codepoint emoji (no modifiers, ZWJ sequences, or flags), and that the whole app is Next.js on Vercel. `apps/web` is on `next@^16.3.1`, resolved to `16.3.4` at the time of writing (`apps/web/package.json`, `node_modules/next/package.json`). `docs/architecture/` does not yet describe routing, so this report is the first written account of how emoji paths behave. Ticket #14 (the Handle model) is blocked on the canonicalisation rule recommended here.

## Findings

### 1. What the browser puts on the wire (WHATWG URL Standard)

The URL Standard defines the *C0 control percent-encode set* as "C0 controls and all code points greater than U+007E (~)", and the *path percent-encode set* as a superset of it (query set plus `?`, `^`, `` ` ``, `{`, `}`). In *path state* the parser runs "UTF-8 percent-encode c using the path percent-encode set and append the result to buffer" for each code point, so every emoji becomes its UTF-8 bytes as `%XX` [S1]. Already-encoded input is not decoded by the parser; `new URL("https://3moji.me/%41").pathname` is `/%41` (checked in Node 24.21.0, whose `URL` is a WHATWG implementation) [S4].

Reproduced in Node 24.21.0: `new URL("https://3moji.me/🧊🧊🧊").pathname` → `/%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A`; `encodeURIComponent("🧊")` → `%F0%9F%A7%8A`; `encodeURIComponent("🧊️")` → `%F0%9F%A7%8A%EF%B8%8F` [S4].

For display, §4.8.3 "Internationalization and special characters" says that parts of the URL other than the host, if rendered, "should have their sequences of percent-encoded bytes replaced with code points resulting from running UTF-8 decode without BOM on the percent-decoding of those sequences, unless that renders those sequences invisible", and that browsers "may choose to not decode certain sequences that present spoofing risks (e.g., U+1F512 (🔒))" [S1]. So a browser may legitimately show some emoji percent-encoded. UTS #58 documents the practical consequence: "many browsers currently don't put the desired Unicode string onto the clipboard, and instead put an unreadable string there", giving `https://www.youtube.com/@%ED%95%91%ED%81%AC%ED%90%81` as the pasted form of `www.youtube.com/@핑크퐁` [S2]. Which form a given browser copies is not specified anywhere and was not tested here (unverified).

### 2. What `params` contains in Next.js 16.3.4 (reproduction)

Set-up: `npm ci`; a temporary `apps/web/src/app/[handle]/page.tsx` that renders `JSON.stringify({ raw: handle, encoded: encodeURIComponent(handle), codepoints, length })` plus two headers set by a temporary `apps/web/src/proxy.ts` (`x-tmp-pathname = encodeURI(request.nextUrl.pathname)`, `x-tmp-href = encodeURI(request.nextUrl.href)`); a temporary `app/tmp-redirect/page.tsx` calling `redirect("/🧊🧊🧊")`, `permanentRedirect("/🧊🧊🧊")`, or `redirect("/%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A")` by query string. All temporary files were deleted before commit. Environment: macOS 26.6.2, Node v24.21.0 (ICU 78.3, Unicode 17.0), Next.js 16.3.4 (Turbopack), curl [S3].

| Request (`curl`)                                  | `next dev` result                                                              | `next build` + `next start` result |
| ------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------- |
| `GET /%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A`       | 200; `raw: "%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A"`, `length: 36`               | identical                          |
| `GET /🧊🧊🧊` (raw UTF-8 bytes on the wire)       | 200; `raw` identical to the row above (upper-case `%XX`)                       | identical                          |
| `GET /%F0%9F%A7%8A%EF%B8%8F` (`🧊` + U+FE0F)      | 200; `raw: "%F0%9F%A7%8A%EF%B8%8F"`, `length: 21` — VS16 is preserved          | identical                          |
| `GET /%F0%9F` (truncated sequence)                | **400** Bad Request                                                            | **500** Internal Server Error      |
| `redirect("/🧊🧊🧊")`                             | **500**; log: `TypeError: Invalid character in header content ["location"]`    | identical                          |
| `permanentRedirect("/🧊🧊🧊")`                    | **500**; same error                                                            | identical                          |
| `redirect("/%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A")` | 307; `location: /%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A`                      | identical                          |

`request.nextUrl.pathname` in `proxy.ts` was percent-encoded in every case. For the percent-encoded requests it was byte-identical to the request (upper-case hex); for the raw-UTF-8 request it was `/%f0%9f%a7%8a…` (lower-case hex) while `params.handle` was upper-case — the two layers normalise the case of `%XX` differently, so never compare `nextUrl.pathname` and `params` byte-for-byte [S3].

The Next.js docs do not state whether `params` are decoded; the Dynamic Route Segments page only says values are typed `string` because "Users can enter any URL into the address bar" [S5]. The shared route matcher `getRouteMatcher` calls `decodeURIComponent` on each captured group and throws `DecodeError('failed to decode param')` on failure [S13], but the App Router's observed behaviour is the encoded form, consistent with the still-open issue #48058 "Special characters are not decoded in dynamic routes using app directory" (opened against 13.3.1-canary, open as of 2026-09-11) [S14]. The exact code path that re-encodes App Router params in 16.3.4 was not traced in this session (unverified); the observed contract is what matters and it is stable across dev and production.

Takeaway: the page owns decoding. `decodeURIComponent(handle)` must be wrapped in `try/catch` (`URIError` on malformed input → `notFound()`), because Next.js only partly guards it (400 in dev, 500 in production for `/%F0%9F`) [S3].

### 3. `<Link>`, `redirect()`, `permanentRedirect()`, and `generateMetadata`

- **`<Link href="/🧊🧊🧊">`** and `<Link href={{ pathname: "/🧊🧊🧊" }}>` both rendered `<a href="/🧊🧊🧊">` — the raw emoji is placed in the attribute and the browser percent-encodes on navigation per Finding 1. A `<Link>` whose `href` is `"/" + handle` with the still-encoded param rendered `<a href="/%F0%9F%A7%8A…">`; no double-encoding occurs because `Link` does not encode a string `href` (`link.tsx` passes it through `addBasePath`/`addLocale` only) [S3, S15]. Both forms navigate to the same route, but only the encoded form is safe to pass to `redirect()`.
- **`redirect(url)` / `permanentRedirect(url)`** do nothing to the string: `getRedirectError` puts it verbatim into the error digest (`${REDIRECT_ERROR_CODE};${type};${url};${statusCode};`) [S6], and Node's `setHeader` then rejects a non-ASCII `Location` with `ERR_INVALID_CHAR` (Finding 2). Issue #80210 reported the same crash on Vercel in 15.4-canary; a Vercel engineer said the Vercel Functions runtime constraint was removed for all customers on 2026-01-25 and that non-ASCII header values would be percent-encoded by the runtime, but our reproduction shows the crash is now Node's own header validation in `next start`, so the rule is unchanged: **always pass the percent-encoded path** to `redirect()`/`permanentRedirect()` [S3, S16]. Next.js uses 307 for `redirect` and 308 for `permanentRedirect` rather than 302/301; both preserve the method [S7]. Behaviour of the fixed Vercel runtime with an *encoded* `Location` was not deployed and tested here (unverified).
- **`generateMetadata`**: `resolveUrl` joins a relative `alternates.canonical` / `openGraph.url` with `metadataBase` via `path.posix.join` and `new URL(joinedPath, metadataBase)`, so the emitted tags are percent-encoded. Reproduced: `alternates: { canonical: "/🧊🧊🧊" }` with `metadataBase: new URL("https://3moji.me")` emitted `<link rel="canonical" href="https://3moji.me/%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A"/>` and `<meta property="og:url" content="https://3moji.me/%F0%9F%A7%8A…"/>`; passing the encoded param produced the same bytes [S3, S8]. Note that `new URL()` would also encode a stray U+FE0F rather than strip it — canonical URLs must be built from the canonical key, not from the received param.
- **Vercel CDN**: the only automatic URL normalisations Vercel documents are collapsing consecutive slashes (308) and *not* lower-casing paths; the docs say nothing about percent-encoding or non-ASCII paths [S17]. The Vercel Redirects and Rewrites docs likewise have no encoding statement (checked 2026-09-11). No Vercel edge mangling of emoji paths is documented; none was observed locally; production on Vercel was not exercised in this session (unverified).

### 4. Unicode: variation selectors, normalisation, and a canonical key

- **Presentation selectors.** UTS #51 defines U+FE0F VARIATION SELECTOR-16 as the *emoji presentation selector* (ED-9) and U+FE0E as the *text presentation selector* (ED-8), and states "The only valid emoji presentation sequences are those listed in the emoji-variation-sequences.txt file" [S9]. That file (Unicode 17.0) contains 371 sequences; `🧊` U+1F9CA is **not** in it, whereas `❤` U+2764, `☺` U+263A, and `☀` U+2600 have both `FE0E` (text style) and `FE0F` (emoji style) entries [S10]. So `🧊️` is not a valid variation sequence at all, while `❤️` is the *fully-qualified* form of a text-default emoji.
- **Default presentation.** UTS #51 §4 splits emoji into *emoji-default* (`Emoji=Yes`, `Emoji_Presentation=Yes`), *text-default* (`Emoji=Yes`, `Emoji_Presentation=No`) and *text-only* (`Emoji=No`), and §2.7.1 says an emoji character "should have an emoji presentation selector added if Emoji_Presentation=No whenever an emoji presentation is desired", and that keyboards should generate only fully-qualified sequences (§1.4.5) [S9]. Node confirms `/\p{Emoji_Presentation}/u` is true for U+1F9CA and false for U+2764 [S4]. Consequence: if the Emoji Set ever includes a text-default character, real keyboards will send it with a trailing U+FE0F, and the same Handle will arrive in two spellings.
- **NFC/NFD do not help.** UAX #15 defines NFC as canonical decomposition followed by canonical composition, and a deterministic comparison of normalised strings as binary equality [S11]. Emoji code points and variation selectors have no canonical decompositions, so normalisation is the identity: `"🧊️".normalize("NFC")` is still `U+1F9CA U+FE0F`, and `"❤️".normalize("NFKC")` is still `U+2764 U+FE0F` (Node 24.21.0, Unicode 17.0 data) [S4]. NFC is still worth applying as a cheap guard for any non-emoji input, but VS15/VS16 removal has to be explicit.
- **Unqualified vs fully-qualified.** UTS #51 ED-18/ED-18a/ED-19 define fully-, minimally- and unqualified emoji; `emoji-test.txt` assigns a status to every RGI emoji "and related sequences with missing variation selectors" [S9]. For a set of *single-codepoint* emoji the distinction collapses to "with or without a trailing selector", which is exactly the case a canonical key must erase.
- **Postgres.** A deterministic collation "considers strings to be equal only if they consist of the same byte sequence"; `C`/`POSIX` sort by byte value and `ucs_basic` by code point [S12]. So `UNIQUE (canonical_key)` means "no two rows with the same bytes" — meaningful iff the application writes only canonical bytes. Postgres also offers `normalize(text, NFC)` and `text IS NFC NORMALIZED` (UTF8 server encoding only) [S18], which can back a `CHECK` constraint, but it cannot strip variation selectors or validate membership in the Emoji Set; that stays in the domain layer.

**Canonicalisation rule (recommended).** Given the received segment `s` (`params.handle`, still percent-encoded):

1. `decoded = decodeURIComponent(s)`; on `URIError` → not a Handle.
2. `nfc = decoded.normalize("NFC")`.
3. `stripped = nfc.replace(/[︎️]/gu, "")` (VS15 and VS16 only; nothing else is removed — a ZWJ, skin-tone modifier, tag, or regional indicator makes the string invalid rather than being silently dropped, because the Emoji Set excludes those forms by decision on #8).
4. `cps = Array.from(stripped)` (iterates by code point, not UTF-16 unit).
5. Valid iff `1 <= cps.length <= 3` and every element is in the Emoji Set (compare code points, not glyphs).
6. Canonical key = `cps.join("")` — the bare code-point sequence, stored as `text COLLATE "C"` with `UNIQUE` and `CHECK (handle IS NFC NORMALIZED)`; canonical path = `"/" + encodeURIComponent(key)` (upper-case `%XX` of the UTF-8 bytes). If an ASCII key is preferred for tooling, `cps.map(c => c.codePointAt(0).toString(16)).join("-")` (e.g. `1f9ca-1f9ca-1f9ca`) is a lossless alternative; either works, but pick one and derive the other.

**Redirect policy (recommended).** In `app/[handle]/page.tsx` (and `generateMetadata`):

- If canonicalisation fails → `notFound()` (404). Do not redirect garbage; it leaks nothing and keeps crawlers from indexing junk.
- If it succeeds and `s === encodeURIComponent(key)` → render the Profile (or 404 if the Handle is unclaimed/Reserved).
- Otherwise → `permanentRedirect("/" + encodeURIComponent(key))` (308). This covers a trailing U+FE0F, lower-case `%xx` hex, and any other non-canonical but resolvable spelling. Pass the *encoded* path — the raw form crashes (Finding 3). 308 is what Next.js offers for "permanent"; it differs from 301 only by forbidding a method change, which is irrelevant for `GET` [S7].
- Build `alternates.canonical` / `openGraph.url` from the canonical key, never from `s`.

### 5. Messaging apps: linkification of `3moji.me/🧊🧊🧊`

- **Apple (iMessage).** Foundation's `NSDataDetector` (`NSTextCheckingType.link`) on macOS 26.6.2 detects `https://3moji.me/🧊🧊🧊`, `3moji.me/🧊🧊🧊` (scheme-less, `http://` assumed), and the percent-encoded form, in each case returning the full range and a percent-encoded `URL` (`https://3moji.me/%F0%9F%A7%8A%F0%9F%A7%8A%F0%9F%A7%8A`); a trailing full stop is excluded [S19]. That Messages uses `NSDataDetector` for tappable links is widely assumed but not documented on the page fetched (unverified); the API behaviour itself is verified.
- **X.** `twitter-text` 3.1.0, X's open-source tokenizer, extracts only `https://3moji.me/` from `see https://3moji.me/🧊🧊🧊 ok` — the path character class is ASCII plus `\p{Cyrillic}`, dashes, and Latin accents, with no symbol or emoji ranges — but keeps the percent-encoded URL intact [S20, S21]. Whether X's production linkifier still matches the library is unverified; assume the emoji path is dropped unless the URL is shared percent-encoded.
- **Slack.** The formatting docs say a URL in `mrkdwn` "will be auto-transformed by the server into a link" and warn only that "URLs with spaces will break"; nothing states which characters end a link or how non-ASCII paths are handled [S22]. Behaviour with an emoji path is unverified.
- **WhatsApp.** No primary source describing link detection was found; the only official-adjacent guidance concerns spam controls that make links from unknown senders non-tappable. Behaviour with an emoji path is unverified.
- **Standard.** UTS #58 *Unicode Link Detection and Formatting* (17.0, 2026-02-02, approved and stable) assigns `Link_Term=Include` to "All other code points" (everything that is not whitespace, control, non-character, unassigned, a bracket, or terminator punctuation), so a conforming detector keeps emoji in the path, and its minimal-escaping algorithm leaves them unescaped [S2]. It also states the design goal that "a detected URL works when pasted into address bars of major browsers". Adoption by the apps above is unverified.
- **Unfurls.** Whatever the client does with the text, the unfurl fetch hits the percent-encoded URL and the page's `og:url` is percent-encoded (Finding 3), so previews resolve as long as the redirect policy sends non-canonical spellings to the canonical page.

## Options

| Option                                                                                   | Pros                                                                                            | Cons                                                                                          | Effort | Risk |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------ | ---- |
| A. Canonicalise in the page; 308 to canonical; 404 otherwise (recommended)               | One place owns the rule; every spelling reaches one Profile; canonical URL is the only one indexed | Adds one redirect hop for VS16 spellings; page must never trust `params` raw                 | L      | L    |
| B. Canonicalise in `proxy.ts` and rewrite (no redirect)                                  | No extra round trip                                                                             | Non-canonical URLs stay in address bars, shares, and search indexes; `nextUrl` case differs from `params`, so two code paths to keep in sync | M      | M    |
| C. Store spellings as they arrive, resolve with a nondeterministic collation             | No app-side rule                                                                                | Collations cannot strip VS16 or validate the Emoji Set; B-tree dedup lost; `UNIQUE` stops meaning what we think | M      | H    |
| D. Serve the percent-encoded form as canonical and show it everywhere                    | Survives every linkifier tested                                                                 | Contradicts the settled product decision that `3moji.me/🧊🧊🧊` is canonical; unreadable     | L      | L    |

## Recommendation

Adopt Option A with the canonicalisation rule and redirect policy in Finding 4, and make three engineering rules explicit in the Handle ADR: (1) `params.handle` is percent-encoded and is decoded exactly once, in a `try/catch`; (2) `redirect()`/`permanentRedirect()` and any `Location`/`Link` header always receive `encodeURIComponent(key)`, never a raw emoji string; (3) canonical/OG URLs are derived from the stored key. Keep the Emoji Set to `Emoji_Presentation=Yes` characters where possible so VS16 never appears in canonical spellings, and treat a VS16 in the allowlist itself as a defect.

For sharing, keep `3moji.me/🧊🧊🧊` as the displayed canonical URL (it is what the product decided and what UTS #58 and Apple's detector favour) but give the copy/share button both forms, defaulting to the percent-encoded one for X and for any client we have not verified. Confidence: high on the Next.js and Unicode findings (all reproduced or quoted from the spec); medium on Vercel (nothing documented contradicts the local reproduction, but production was not exercised); low on WhatsApp and Slack (unverified). What would change the recommendation: a Next.js release that decodes App Router `params` (issue #48058) would move step 1 into the framework but not change the rule; a Vercel edge normalisation of `%XX` case would make the byte comparison in the redirect policy redirect more often, never wrongly.
