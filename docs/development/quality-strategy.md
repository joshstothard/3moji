## Test Pyramid

| Layer       | Scope                                            | Runs                                                                             |
| ----------- | ------------------------------------------------ | -------------------------------------------------------------------------------- |
| Unit        | One function/class, all dependencies mocked      | pre-push, CI on every push                                                       |
| Integration | Module + real infrastructure (DB, queue) locally | CI on every push                                                                 |
| E2E         | Full stack through the browser                   | CI on every push                                                                 |
| Mutation    | The tests themselves (Stryker or equivalent)     | full run on demand (`nightly-mutation` workflow, manual dispatch — see ADR-0002) |
| Security    | OWASP scanning, dependency audit                 | CI on every push                                                                 |
| A11y        | WCAG AA via axe-core or equivalent               | CI on every push                                                                 |

## Standards

- **Coverage floor:** 70% unit coverage. Never reduce it.
- **Observed red:** every test is seen failing for the right reason before it counts (see `AGENTS.md` § TDD Workflow).
- **Scripts that make decisions are unit-tested:** `scripts/*.test.mjs` run under Node's built-in test runner (`npm run test:scripts`), in `scripts/verify.sh` and CI. Keep the decision a pure function the tests can call without GitHub or the network, as `scripts/auto-merge.mjs` does with `evaluate()`.
- **Every workspace is linted, and a guard proves it.** `npm run lint` is `turbo lint`, which runs each workspace's own `lint` script — a workspace without one is skipped in silence, not reported, so the repo's standards never reach it. `packages/shared` was in that state from creation until [#40](https://github.com/joshstothard/3moji/issues/40): shared types, Zod schemas and constants that the domain and the web app both import, never linted, locally or in CI. A new package therefore ships `eslint.config.mjs` (three lines, re-exporting `@template/eslint-config`), a `"lint": "eslint src"` script, and a `tsconfig.json` that includes the files being linted — type-aware rules cannot parse a file belonging to no project. `scripts/lint-coverage.test.mjs` asserts this against `turbo run lint --dry=json`, which reports `"command": "<NONEXISTENT>"` for a workspace with no script behind it, so a missing script, a deleted one, and a workspace dropped from the `workspaces` globs all fail the same check. Exemptions are an allowlist in that file, each with a reason; the config-only packages (`tsconfig`, `eslint-config`, `jest-config`) are the current entries, and the guard also fails on a **stale** exemption, so the allowlist cannot quietly outlive its reason.
- **A shared working file is a silent failure.** A sub-agent's scratchpad directory is keyed on the parent session, so sibling agents share it: two agents each wrote their pre-review to `review.md`, one clobbered the other between writing and posting, and the wrong review landed on a pull request ([#66](https://github.com/joshstothard/3moji/issues/66)). Take a `mktemp` path for anything written and read back, or scope the name to the issue or PR, and check a body names its target before posting it. `npm run verify:agents` asserts no skill posts from an unnamed `--body-file <file>` placeholder. The general rule: **anything read back from disk must be verified to be the thing you wrote**, because a clobber is indistinguishable from success until it is public.
- **Absence of evidence is never success.** A gate that asks "is anything still failing?" and receives an empty answer must report _unknown_, not _green_. `gh pr checks` has been observed printing "no checks reported on the branch" for a PR whose head commit had ten check runs in flight, and every idiom built on it — `[.[] | select(.bucket == "pending")] | length`, or "every check is SUCCESS" — is satisfied **vacuously by an empty list**, so the gate reads a PR with running CI as ready to merge (#71). Read the head commit's check runs and require `total_count > 0`. `scripts/auto-merge.mjs` is the model: `ciProblem()` returns `ci-missing`, `ci-stale` or `ci-running` rather than falling through. `npm run verify:agents` asserts the unsafe idiom does not return to any skill's runnable code block.
- **Tests assert behaviour, not implementation** — a test that breaks on refactor without a behaviour change is a bad test.
- **Mutation testing keeps the tests honest:** coverage proves code was executed; mutants prove the assertions actually constrain it. Surviving mutants are reported by the full Stryker run, dispatched manually from the Actions tab (its nightly schedule is disabled per ADR-0002).
- **Flakes are defects:** a test that fails non-deterministically more than twice in 7 days gets a GitHub issue (see `nightly-check`).
- **No hard-coded credentials in tests:** tests read credentials from environment variables and throw clearly when absent. The only exception is a mocked secrets provider returning fixture values.

## Domain unit tests (`packages/core`)

Domain tests run under Jest + ts-jest in the `node` environment, from `@template/jest-config/base`.

- **`better-auth` is ESM-only, so the `test` script needs `--experimental-vm-modules`.** The script is `node --experimental-vm-modules ../../node_modules/jest/bin/jest.js --coverage` — Jest's documented form, and portable to Windows `cmd.exe` unlike an inline `NODE_OPTIONS=` prefix. Without the flag every suite that touches Better Auth fails before a single test runs, with `Must use import to load ES Module`. Run the tests through `npm test`, not bare `npx jest`, and note that anything spawning Jest itself (a Stryker runner, an IDE) does not inherit the flag and must pass it. This is the same workaround the deleted NestJS app needed, for the same reason.
- **Framework-free does not mean dependency-free.** `packages/core` holds no _framework_, which is what ADR-0006 requires and what its ESLint config enforces. It does hold the auth library and the database driver, and those bring their own module-format constraints.

- **`packages/core` is framework-free, and its ESLint config enforces that** — any import of `next/*`, `react`, `react-dom` or `@vercel/*` fails the build, type-level imports included.
- **The boundary rules are themselves pinned by a test, because a lint rule can stop working silently.** `src/architecture/framework-free-boundary.test.ts` writes throwaway fixtures into a temporary directory under `packages/core` (outside `src`, so `collectCoverageFrom` cannot count one mid-run as uncovered source), lints them by spawning the real ESLint CLI from `packages/core` — the same config resolution `npm run lint` gets — and asserts on the **rule name and severity** in the JSON output — severity because a rule downgraded to `"warn"` still produces a message but stops failing `npm run lint`. Asserting only "lint failed" would be satisfied by any unrelated error, which is how the first manual proof in #29 was contaminated. Three properties are pinned: `no-restricted-syntax` fires on `typeof import("next/headers")` (the `TSImportType` selector, whose typescript-eslint AST shape is not a contract and would otherwise rot silently), `no-restricted-imports` fires on both `import type … from "next/headers"` and `import { createElement } from "react"`, and a **safe fixture (`typeof import("node:crypto")`) lints with zero messages** — which both proves the rules are not over-matching and turns a pre-existing lint error into a loud "contaminated baseline" failure rather than a false green.
- **Collaborators are injected, never reached for.** Anything the domain needs from outside is a port in `src/ports/`, implemented by an adapter in `src/adapters/`, and wired by the composition root. Tests pass a fake in rather than patching a module.
- **Time is injected.** The `Clock` port exists because rules like a Handle's 24-hour hold and 30-day cooldown ([ADR-0004](../adr/0004-the-handle-model.md)) are untestable if the domain reads the system clock.
- `tsconfig.json` declares `"types": ["node", "jest"]`. Without it, type-aware lint rules cannot resolve `expect` and report every assertion as an unsafe call — a failure that looks like a code smell but is a config gap.
- **`tsconfig.json` also includes `drizzle.config.ts`.** A `.ts` file outside the project cannot be parsed by the type-aware linter, and the pre-commit hook lints staged `.ts` files, so a config left out of `include` blocks the commit with a parsing error rather than a real finding.
- **The canonical key is covered by properties, not examples.** `canonicalise` is the function the `UNIQUE` index's meaning rests on, so `src/handle/canonicalise.property.test.ts` uses **`fast-check`** (a `devDependency` of `@template/core`; the CJS build works under the existing ts-jest transform) to generate Handles from the released set and round-trip them through presentation selectors, NFC/NFD and percent-encoding. Round-trip stability is only half of it: it catches over-strictness but **cannot catch collapse**, which is the failure that loses a Claim, so the suite also asserts injectivity — a reordered Handle and a one-position change must both give a different key. A `[...triple].sort()` mutation of the key survives the stability property and is killed only by those. Example-based tests live beside them in `canonicalise.test.ts` for the cases a generator drawing from the released set can never emit: malformed percent-encoding, a ZWJ sequence that is exactly three code points once the selectors are stripped, a skin-tone modifier, and an unreleased category.
- **Generated data is tested against its source, not against a snapshot.** `src/emoji/emoji-candidates.generated.ts` is produced by `scripts/generate-emoji-set.mjs` from the candidate report. `emoji-set.test.ts` reparses that report and asserts the shipped module equals it entry for entry, which is what proves the 1,053 entries are derived rather than retyped; the generator's own test asserts its output is byte-identical to the committed file, so Prettier never introduces a phantom diff on commit. A test parameterised on the value it constrains constrains nothing — the unreleased-category tests spell the five categories out rather than deriving them from `RELEASED_CATEGORIES`, so releasing one turns them red.
- **Hand-authored data carries a redundant field so a mis-keyed row is catchable.** The curated emoji names (`src/emoji/emoji-curation.ts`) are keyed by code point, and the set contains near-identical glyph pairs — 🐵/🐒, 🐶/🐕, 🐱/🐈, 🐭/🐁/🐀. A row attached to the wrong key still has a non-empty display name, a plural and a unique name, so every obvious assertion passes while the product says the wrong word. Each row therefore repeats the CLDR name it believes it is curating, and a test asserts that against the set. The same test asserts the row set equals the released set exactly, in both directions, because a silently missing row is the other half of that failure.
- **The schema is tested against the library, not against a document.** `schema.test.ts` calls Better Auth's own `getAuthTables()` and asserts our Drizzle tables against it. Its adapter addresses columns by Drizzle **property key**, so a rename is a runtime failure in production rather than a type error at build time; this is the only cheap way to catch that.

## Integration tests (`packages/core`)

Integration tests are named `*.integration.test.ts` and run under `jest.integration.config.mjs`, separate from the unit suite. CI's `integration-tests` job provides a `postgres:16` service and sets `DATABASE_URL`.

- **They never drop a schema or a table.** Resetting the database is how such suites usually start, and it turns a misaimed `DATABASE_URL` into data loss. Drizzle's migrator is idempotent, which is the property worth asserting anyway, so the suite works against a fresh database and an already-migrated one alike.
- **A missing `DATABASE_URL` skips locally but throws in CI.** A green run that tested nothing is worse than a red one, so the suite fails loudly when `CI` is set and no database is configured. That guard earned its place immediately: it caught the next bullet.
- **Turborepo runs tasks in strict environment mode, so a variable CI sets does not reach the test.** Turbo 2.x passes only the variables declared in a task's `env` (plus its own allowlist), so `DATABASE_URL` set on the CI step was silently stripped and every integration test skipped. `turbo.json` now declares `env: ["DATABASE_URL", "REDIS_URL"]` on `test:integration`. **Any future task that needs a new variable must declare it there**, or it will read as undefined with no error. Verify the plumbing without a database by pointing `DATABASE_URL` at a closed port: the tests should fail to connect, not skip.
- **Better Auth's two link shapes differ, and only a real run reveals it.** Verification puts the token in a query parameter (`/verify-email?token=…`); password reset puts it in a **path segment** (`/reset-password/<token>?callbackURL=…`). A helper that handles only the query form passes every verification test and fails every reset test.
- **`--experimental-vm-modules` runs ESM in its own realm, so `toBeInstanceOf(Error)` is unreliable.** An `Error` raised inside the database driver is not the test realm's `Error`, and the failure reads `Expected constructor: Error, Received constructor: Error` — which looks like a Jest bug rather than the realm boundary it is. Assert on a property instead (`message`, `code`), narrowed from `unknown`, and **walk the `cause` chain**: Drizzle reports a failed statement as "Failed query: …" and keeps the driver's error, the one carrying `ECONNREFUSED` or the SQLSTATE, in `cause`. **An error that has left an adapter — ours, or Better Auth's since [#148](https://github.com/joshstothard/3moji/issues/148) — is different:** it is `DatabaseQueryFailed`, with the code as its own `code` property, a message naming only that code, and no `cause` at all ([#144](https://github.com/joshstothard/3moji/issues/144)) — so assert on `code` (or `postgresErrorCode`, which reads it first), and never on text from the driver. `database-error-boundary.test.ts` shows how to get a real `DrizzleQueryError` without a database: a closed port for a query, or a pool whose client answers `begin` and rejects the next statement with a `pg` `DatabaseError`.
- **The unit suite excludes them** via `testPathIgnorePatterns`, and `collectCoverageFrom` excludes test files — otherwise an integration test that does not run in the unit suite is counted as 0% and drags the package under its coverage threshold.

## Web unit tests (`apps/web`)

Web tests run under Jest + `jest-environment-jsdom` with React Testing Library. Conventions:

- **Async server components** are rendered by awaiting the component function and passing the result to `render` — e.g. `render(await SomePage())`, or `render(await SomePage({ params: Promise.resolve({ id }) }))` for pages that take `params`.
- **Jest cannot parse CSS.** A Next.js layout imports global styles, so `@template/jest-config/nextjs` maps stylesheets to `packages/jest-config/style-mock.js`. Without that mapping a layout test fails at import, before any assertion runs.
- **Data access is mocked at the module boundary:** `jest.mock("../../lib/okr-api", …)` — presentational components receive data, they do not fetch, so tests drive them by mocking the API client. For `fetch`-based units, assign `global.fetch = jest.fn()` (jsdom does not provide it) and resolve a minimal `{ ok, status, json }` object.
- **Server-action helpers are never invoked in unit tests.** `next/cache` and `next/navigation` are mocked globally in `jest.setup.ts` so importing a page does not drag in the full Next server runtime; `TextEncoder` is polyfilled there for the same reason.
- **jest-dom matcher types** (`toBeInTheDocument`, `toHaveAttribute`) are pulled into the TS program via `src/types/jest-dom.d.ts`, because `jest.setup.ts` lives outside `src` and its augmentation would otherwise be invisible to `tsc`/eslint.
- **Components are checked by axe for WCAG 2 A and AA, in files named `*.a11y.test.tsx`** ([#152](https://github.com/joshstothard/3moji/issues/152)). They run in this suite, so in the Unit tests CI job, through `src/test-support/axe.ts`, which calls `axe-core` directly (a pinned `devDependency` of `apps/web`; `jest-axe` would add two more copies of the engine, one of them `axe-core@3` via its types). Each check asserts three things: no violations, no `incomplete` results, and that named rules (`button-name`, `label`, `list`…) actually **passed** — because a check whose rules found nothing to apply to is green and proves nothing. Axe is scoped to the render container, never to `document`, and the rules jsdom cannot evaluate are disabled by name in `RULES_JSDOM_CANNOT_EVALUATE`: colour contrast, link-in-text-block, target size, scrollable regions, orientation lock and p-as-heading need layout, colour or stylesheets, and the document-title, `lang`, bypass, meta and `aria-hidden-body` rules are page-level. **None of those is covered here**, and nor are focus visibility or duplicate ids across a page; the rendered-page check in [#153](https://github.com/joshstothard/3moji/issues/153) covers them. The views that are private to `app/[handle]/page.tsx` (the Profile, the unedited Handle, the alias listing) are checked through the route with its collaborators faked, rather than by exporting them.
- The 70% coverage floor applies to the whole `apps/web` `src` tree — page/layout server components included — so new pages ship with tests.

## End-to-end tests (`apps/web/e2e`)

Specs run under Playwright from the root `playwright.config.ts`, against `npm run dev` on port 3000, in two projects (`chromium` and `Pixel 7`). `npm run test:e2e` passes `--pass-with-no-tests`.

- **The `e2e` directory is inside the TypeScript project and is linted.** `apps/web/tsconfig.json` includes `e2e/**/*` and the package's lint script is `eslint src e2e`. Without the `include`, a spec is invisible to `tsc` _and_ unparseable by the type-aware linter, so the pre-commit hook — which lints every staged `.ts` file — fails with `"parserOptions.project" has been provided… file was not found`, which reads as a lint finding rather than the config gap it is. This is the same trap `packages/core`'s `drizzle.config.ts` hit.
- **A spec asserts bytes, not markup, wherever a status code or header is the behaviour.** Use `request.get(url, { maxRedirects: 0 })` and assert the status and `Location`; a `page.goto` that silently follows a redirect cannot tell a 308 from a 200.
- **E2E is where the real domain meets the real route.** Web unit tests mock `@template/core` (it cannot be `require`d under Jest), so the Handle route's unit test proves only which branch each canonicalisation result takes. `handle-url.spec.ts` is the only place the genuine `canonicalise` answers a genuine HTTP request.
- **CI's E2E job runs the real app against a migrated Postgres** ([#151](https://github.com/joshstothard/3moji/issues/151)). It applies the committed Drizzle migrations with `drizzle-kit migrate` before any spec runs, and sets all five variables `lib/services.ts` requires — `DATABASE_URL`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`, `RESEND_API_KEY`, `RESEND_FROM` — with **obviously fake values written inline in the workflow, never repository secrets**. Playwright starts the app with `npm run dev`, which is `turbo dev`, and Turborepo's strict env mode hands a task only the variables it declares — so the `dev` task lists these six in `passThroughEnv` in `turbo.json`, or `next dev` would start without them and every database read would quietly degrade to "unknown". The repository and its Actions logs are public, so none of them may be reused anywhere real, and no step echoes one.
- **E2E email goes to a recording sender, never Resend.** The job sets `TEST_EMAIL_SENDER=recording`, and `lib/services.ts` wires `createRecordingEmailSender` in place of Resend. **Production refuses the switch:** with `NODE_ENV=production` or any `VERCEL_ENV`, service construction throws, so it cannot become a way to switch email off — `services.test.ts` proves it. The switch is selected explicitly and `NODE_ENV` only ever refuses it, which is the difference from the `NODE_ENV`-chosen driver ADR-0010 removed. There is deliberately no route for reading captured mail: it would be a new public surface, and the seed helper below reads its own.
- **Seed through the domain, with `e2e/support/seed.ts`.** `seedClaimedHandle({ profile? })` claims a random, fresh Handle with `claimHandle`, verifies it with `finaliseClaim` (reading the token from its own recording sender), saves the Profile with `editProfile`, and returns `{ key, path, emoji, profile, credentials }` — `path` percent-encoded for `request.get`, `emoji` carrying the names the picker labels them by. It never writes SQL, so the Reserved Handle check, the one-Account-one-Handle transaction and the Profile limits all hold in seeded data. Each call picks a new Handle, so both Playwright projects and retries never collide. **The database is shared by every spec for the whole job**, so a Handle one spec claims is visible to all the others: an alias a spec relies on staying unclaimed lives in `e2e/support/aliases.ts`, and a spec that seeds under a random alias excludes it. The alias listing check once picked `apple.apple.apple` at random and failed `handle-url.spec.ts` on every attempt ([#177](https://github.com/joshstothard/3moji/issues/177)). It imports `@template/core` from `packages/core/dist`, which is why the build job's artifact carries that directory: Playwright does not resolve with the `development` condition Next.js uses.
- **Rendered pages are checked by axe for WCAG 2 A and AA, in `accessibility.spec.ts`** ([#153](https://github.com/joshstothard/3moji/issues/153)). `e2e/support/axe.ts` runs `@axe-core/playwright` (a pinned `devDependency` of `apps/web` that resolves the same `axe-core@4.13.0` as the component check, so there is one copy of the engine) over the whole document in real Chromium, with the `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa` tags, **no rule disabled and nothing excluded**. It is where the rules the component check cannot evaluate actually run: colour contrast from the real CSS, target size, `bypass`, the document title and `lang`. It checks `/` with the picker, a seeded claimed Profile, and an alias listing — two Handles seeded through `seedClaimedHandle({ chooseEmoji })` from the candidates of an alias whose term names several emoji, picked from `aliasTermSlugs()` rather than hard-coded. Each check asserts no violations, no `incomplete` results, and that the rules in `PAGE_RULES` plus page-specific ones passed; a self-test injects an unlabelled input and asserts the check reports `label`. `landmark-one-main` and `region` are axe `best-practice` rules, not WCAG, so the tags never load them; `bypass` is the WCAG 2.4.1 rule for landmarks. Since [#177](https://github.com/joshstothard/3moji/issues/177) the two landmark rules run by name on all three pages in a second pass, `checkLandmarks`, under the same three assertions and with nothing excluded; the whole `best-practice` tag is still not enabled.
- **What axe cannot see has its contrast measured, in `accessibility.spec.ts`** ([#177](https://github.com/joshstothard/3moji/issues/177)). axe does not reliably evaluate `::placeholder`, and it skips a glyph hidden with `aria-hidden`, so `e2e/support/contrast.ts` measures them from the rendered page: the colour from `getComputedStyle` (with `"::placeholder"` for the pseudo-element), and the backdrop from every ancestor's background. Chromium reports Tailwind v4 colours as `lab()`/`oklch()`, so each is painted onto a 1x1 sRGB canvas and read back rather than parsed, which also composites translucent layers as they render; the helper throws rather than guess through a background image or reduced `opacity`. It asserts 4.5:1 for the picker's search placeholder on `/` and for the Profile edit form's drag handle, reached by signing a seeded owner in through `/sign-in` with the `credentials` `seedClaimedHandle` returns. Each measurement is printed to the job log.
- **Every text field's border is measured against WCAG 1.4.11's 3:1, in `accessibility.spec.ts`** ([#182](https://github.com/joshstothard/3moji/issues/182)). No field has another cue that identifies it as a control — an unfilled field's fill is the surface behind it (1.00:1), the picker's white fill is 1.05:1 on `slate-50`, and `shadow-sm` peaks at 1.27:1 — so the border is the cue, and `measureBorderContrast` in `e2e/support/contrast.ts` measures it against both the surface behind the field and the field's own fill and asserts on the lower. It refuses a border that is not drawn (style `none`/`hidden` or no width) or whose sides differ, because `getComputedStyle` reports a colour either way. It covers the picker search on `/`, the claim form on an unclaimed Handle, the hold screen's resend field, the sign-in fields (without submitting), the share link's manual-copy field (reached by making the clipboard refuse), and the Profile edit form's display name, bio and first Link — the last inside the drag-handle test, so **the suite still signs in through the form once per Playwright project**, which matters under the sign-in rate limit. Fields use `border-slate-500`: `slate-400` measures 2.63:1 on white and 2.51:1 on `slate-50`. The Handle builder's buttons are measured the same way ([#185](https://github.com/joshstothard/3moji/issues/185)): their white fill and `shadow-sm` identify nothing on `slate-50` either, so every slot is measured empty (its dashed border; there is no glyph) and again filled, and every swap suggestion for a seeded taken Handle, all at `border-slate-500` too. The assertions are `expect.soft`, so one run reports every control. The navbar's and footer's `border-slate-200` rules are decorative separators, not control boundaries, and are not measured. There is no password reset form yet, so none is measured.
- **CI's E2E job uses the `list` reporter alongside `html`**, so the job log names every spec and project that ran; the html report is still uploaded as an artifact.
- **`smoke.spec.ts` is the spec that fails when the environment does.** Every other spec passes against an app that cannot reach its database, because the pages degrade honestly. The smoke spec asserts what only a working environment produces: the builder reading a seeded Handle as taken (and never "we could not check"), and a seeded Profile rendering at its Handle.
- **`keyboard-only.spec.ts` drives the picker with the keyboard and nothing else** ([#154](https://github.com/joshstothard/3moji/issues/154)). From `/` it fills three slots, takes a swap suggestion for a seeded taken Handle, and reaches the claim form, asserting `toBeFocused` and a visible focus indicator at every step. Two guards keep it honest: a static one fails the spec if its own source calls a pointer, synthetic-input or programmatic-focus API, and a runtime one records every pointer, mouse and touch event the page receives and requires none. **A focus indicator is a visible outline** — `outline-style` not `none`, a non-zero width, a non-transparent colour — drawn only while focused. Box-shadow does not count, because every control wears `shadow-sm` regardless of focus, and a changed `outline-width` or `outline-color` alone does not either, because Chromium’s own `:focus-visible` rule changes both while leaving the style `none`; a draft that accepted either stayed green against a picker whose focus ring had been deleted. It runs in both projects: `Mobile Chrome` is emulation, not a phone or TalkBack, and stands for an external-keyboard or switch user on a narrow, touch-capable screen.
